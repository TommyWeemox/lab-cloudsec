# S03 : Pipeline OIDC et identités d'application

Date : 19 et 20 novembre 2026 (en cours)

État : identités et fédérations créées dans le portail. Pipeline (E5, E6, E8) reportée
après la formation Terraform.

## Objectif
Permettre à GitHub Actions de déployer sur Azure sans aucun secret stocké, avec des
droits au plus juste, et automatiser plan, apply et destruction des ressources
éphémères.

## Fait
- Groupe de ressources `rg-lab-identity-frc`.
- Deux identités managées affectées par l'utilisateur, sans aucun secret :
  - `id-lab-github-oidc-plan` : fédération `fc-github-pr`, sujet
    `repo:TommyWeemox@<owner-id>/lab-cloudsec@<repo-id>:pull_request` ;
  - `id-lab-github-oidc` : fédération `fc-github-env-lab-apply`, sujet
    `...:environment:lab-apply`.
- Format de sujet immuable (ID du compte et du dépôt), recommandé par Microsoft.
- Rôles :
  - plan : Lecteur sur l'abonnement, Contributeur de données Blob du stockage sur le
    conteneur `tfstate` ;
  - apply : Contributeur sur l'abonnement, Contributeur de données Blob du stockage sur
    le conteneur `tfstate`.
- En S04 : Role Based Access Control Administrator avec condition (seul Key Vault
  Secrets User attribuable) pour l'identité apply, sur le coffre bac à sable.

## Appris
- OIDC : GitHub émet un jeton signé décrivant le job ; Entra vérifie la signature (clé
  publique de GitHub, JWKS) puis compare émetteur, sujet et audience à la fédération.
- La signature prouve que le jeton vient de GitHub ; seul le sujet prouve qu'il vient
  de ce dépôt et de ce contexte.
- Un JWT est signé, pas chiffré : son contenu est lisible.
- Identité managée : identité Entra pour un programme, sans mot de passe, droits par
  RBAC.
- Séparer lecture (pull request, code non relu) et écriture (main et approbation).

## Écarts avec le cahier
Le cahier demande une seule identité, réalisée autrement :

| Cahier | Réalisé |
|---|---|
| Objet application et service principal (E1) | Deux identités managées affectées par l'utilisateur |
| Trois fédérations : pull_request, environment:lab, environment:lab-destroy (E2) | Deux fédérations, sur deux identités : pull_request et environment:lab-apply |
| Contributeur, rôle custom de verrous, Blob Data Contributor (E3) | Lecteur ou Contributeur, Blob Data Contributor, pas de rôle custom |

Décision à prendre et à consigner dans un ADR : garder la séparation en deux identités
(plus restrictive pour les pull requests) ou revenir au modèle du cahier, et dans ce
cas renommer l'environnement en `lab` et ajouter `lab-destroy`.

## Reste à faire

- Vérifier les attributions de rôles avec `az role assignment list`.
- E4 : rôle custom de verrous, assignable sous mg-workloads.
- E7 : consentement utilisateur limité, demandes de consentement administrateur,

- E5, E6 : workflow plan sur pull request (fmt, validate, TFLint, Checkov, plan en
  commentaire), apply après merge avec approbation.
- E8 : workflow de destruction des groupes `lifecycle=ephemeral`.
- Ruleset : plan réussi obligatoire avant merge.
- Dette : identités créées dans le portail, hors IaC.

## Questions
Q3.1 : Objet application, service principal, identité managée : quelles différences ?
L'objet application est la définition globale de l'application. Le service principal
est son instance dans un tenant, celle qui reçoit les rôles. Une identité managée est
un service principal géré par Azure, sans secret, rattaché à une ressource ou
autonome (affectée par l'utilisateur).

Q3.2 : Quel subject OIDC présente un job qui utilise l'environnement lab ?
`repo:<compte>/lab-cloudsec:environment:lab`, ou avec le format immuable
`repo:<compte>@<owner-id>/lab-cloudsec@<repo-id>:environment:lab`.

Q3.3 : Que résout le workflow de demande de consentement administrateur ?
Les utilisateurs ne consentent plus seuls à des permissions sensibles, sans être
bloqués : ils demandent, un administrateur désigné approuve ou refuse.
